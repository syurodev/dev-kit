## Mục đích sinh ra

Hiện tại, kết quả mọi tool call trong transcript của Agent Hub — dù agent gọi
`codegraph.getApiFlow`, `api.send`, `git.diff` hay bất kỳ MCP tool nào — đều
render theo cùng một đường: icon chọn theo từ khóa chung chung trong `kind`
(read/edit/exec/search/fetch), nội dung hiển thị dưới dạng JSON/text thô
(`AgentToolCall.tsx`, `formatToolOutput`). Không có gì phân biệt "đây là dữ
liệu từ Code Graph" với "đây là dữ liệu từ API Client".

Hệ quả: khi agent build một request qua `api.send` hoặc đọc call chain qua
`codegraph.getApiFlow`, người dùng chỉ thấy một khối JSON — không bấm mở lại
được trong API Client, không xem nhanh được flow trong Code Graph. Muốn dùng
tiếp thông tin đó, người dùng phải tự chuyển sang module kia và tra lại thủ
công.

**ToolResultView** là cơ chế cho phép mỗi module đăng ký cách hiển thị riêng
cho kết quả của (các) MCP tool nó sở hữu, để những kết quả đó xuất hiện ngay
trong transcript dưới dạng card có thể tương tác được, thay vì JSON tĩnh.

Nó đi **ngược chiều** với [`agent.attach`](/dev-kit/cross-module) (đã triển
khai — xem [syurodev/dev-kit#122](https://github.com/syurodev/dev-kit/pull/122)):

| | Chiều dữ liệu | Thời điểm |
| --- | --- | --- |
| `agent.attach` | Ref từ module khác → vào composer | Trước khi gửi turn |
| `ToolResultView` | Kết quả tool call → hiện trong transcript | Sau khi agent nhận kết quả |

Hai cơ chế bổ sung cho nhau: `agent.attach` đưa ngữ cảnh vào cho agent đọc;
`ToolResultView` đưa kết quả agent tạo ra trở lại cho người dùng dùng tiếp.

## Quy tắc và giới hạn

1. **Không renderer → fallback JSON generic, không bịa.** Một tool chưa có ai
   đăng ký renderer thì vẫn hiện đúng như hôm nay (`ToolOutput` /
   `formatToolOutput`). Không có đường đoán-format-theo-cấu-trúc — giống
   nguyên tắc của `refResolutionHint` bên `agent.attach`: không có thì nói
   thẳng là chưa có, không tự bịa ra cách hiển thị sai.
2. **Renderer chỉ đọc `RawInput`/`RawOutput`/`Content` đã có sẵn trong
   `ToolCall`.** Không gọi thêm API, không fetch thêm dữ liệu ngoài những gì
   tool đã trả về — nếu cần dữ liệu mới hơn, đó là việc của agent (gọi lại
   tool), không phải của UI.
3. **Keyed theo `ToolCall.Name`, không phải `kind`.** `kind`
   (read/edit/exec/search/fetch/think) là phân loại chung của ACP cho mọi
   tool (kể cả tool riêng của Claude như Read/Edit/Bash); `Name` mới là tên
   tool thật (có sẵn từ 0.77, xem `internal/agenthub/update.go`) và là thứ
   duy nhất DevKit kiểm soát được — vì chính DevKit đặt tên tool khi đăng ký
   với MCP server (`codegraph.getApiFlow`, `api.send`...).

   Trên transcript thật, `Name` không đến nguyên dạng: Claude báo nó dưới
   dạng `mcp__devkit__codegraph_getApiFlow` — tiền tố `mcp__devkit__` cộng
   mọi dấu `.` đổi thành `_`. Phép biến đổi này **chỉ đi xuôi**: registry
   (`registerToolResultView`) tự tính trước dạng dây từ đúng tên Go mà module
   truyền vào, rồi lưu vào một map để so khớp `call.name` — không đoán ngược
   từ chuỗi trên transcript, vì nhiều tên có nhiều dấu chấm
   (`tasks.board.list`) hoặc tự có sẵn `_` (`notes.set_organization`), đoán
   ngược sẽ mơ hồ. `internal/mcp/tool_names_test.go` khoá điều kiện duy nhất
   phép biến đổi này cần: không có hai tên tool Go nào biến đổi ra cùng một
   dạng dây.
4. **Không thay thế 3 content type cố định của ACP** (`content`/`diff`/`terminal`
   — do vendor quyết định khi báo tool call). ToolResultView là một lớp phủ
   THÊM lên trên nhánh `content`/rawOutput hiện có, không đổi wire format
   ACP, không cần vendor hợp tác gì thêm.
5. **Đúng ranh giới `internal/arch`.** Renderer là code frontend thuần (không
   đụng Go); phần Go duy nhất liên quan là `ToolCall.Name`/`RawOutput` vốn đã
   tồn tại — không thêm import chéo, không thêm field mới ở backend cho việc
   này. Ngoại lệ duy nhất: `internal/mcp/tool_names_test.go` — một test đọc
   nguồn `tools_*.go` bằng regex (không import gì mới, không chạm layering)
   để khoá điều kiện mà phép biến đổi tên ở rule 3 cần đúng mãi mãi: không có
   hai tên tool nào biến đổi ra cùng dạng dây.
6. **Ai sở hữu tool, người đó đăng ký renderer** — không có renderer "dùng
   chung" cho nhiều module đoán ý nhau. Xem mục Cách tương tác.

## Cách tương tác

Một registry nhỏ, cùng mẫu với `registerAttachIntent`/`registerIntent` đã có
trong `frontend/src/workbench/intents.ts` — sống ở
`frontend/src/workbench/toolResultViews.ts`:

```ts
// Không phải ToolCall của Agent Hub (frontend/src/modules/agenthub/types.ts):
// một kiểu trung lập riêng, chỉ ba trường renderer được phép đọc (rule 2) —
// để module sở hữu tool không phải import type từ module Agent Hub.
type ToolResultInput = {
  name: string;               // toolNameOf: dạng dây của Claude, hoặc tên Go (Codex)
  rawInput: unknown;
  rawOutput: unknown;         // payload đã bóc của toolPayloadOf — xem mục "Payload"
  content?: ToolContentBlock[]; // khối nội dung của call: ảnh nằm ở đây
  status?: string;
  heading?: string;           // động từ của activity khi card đứng riêng
};
type ToolResultRenderer = (input: ToolResultInput) => React.ReactNode | null;

registerToolResultView("codegraph.getApiFlow", ({ rawOutput }) => {
  const parsed = parseApiFlow(rawOutput); // guard thuần, không React — trả null nếu rawOutput hỏng/bị cắt
  return parsed ? <ApiFlowResultCard flow={parsed.flow} endpointId={parsed.endpointId} /> : null;
});
```

`parseToolOutput` (cùng file) lo hai việc renderer nào cũng cần: bóc lớp
`{"result": …}` mà `structured()` (`internal/mcp/result.go`) bọc quanh một
kết quả không phải object/struct (slice, string, number), và parse trường
hợp `rawOutput` đến dưới dạng chuỗi JSON thay vì object đã parse sẵn (tool
riêng của vendor, hoặc một preview bị cắt được `previewRaw`
(`internal/agenthub/service.go`) mã hoá lại thành chuỗi). Trả `null` khi
không parse được — kể cả khi bị cắt giữa chừng bởi `ToolRawPreviewLimit`
(8KB) — để renderer rơi về JSON thay vì hiện một tài liệu nửa vời.

### Payload: một cách đọc cho mọi vendor

Cùng một kết quả tool DevKit đến transcript theo ba dạng: Claude để trống
`rawOutput` và đặt kết quả ở `content[].content.text` (lỗi là AppError bọc
trong ```` ``` ````); Codex đặt nguyên MCP result vào `rawOutput`
(`{content, structuredContent}`, lỗi `{error}`, quá 64 KiB thành stub
`{truncated, bytes}`) và không có `name`, chỉ có title `devkit.<tool>`; vendor
khác để payload ở `rawOutput`. `frontend/src/workbench/toolPayload.ts` đọc cả
ba một lần, để không view nào phải biết mình đang nhìn vendor nào:

- **`rawOutput` view nhận là payload đã bóc** của `toolPayloadOf` —
  object/array đã parse, envelope `{"result": …}` đã gỡ. Payload không phải
  JSON (vd `pdf.readText`) **vẫn là chuỗi**: đọc nó như chuỗi, vì
  `parseToolOutput` sẽ trả `null` cho nó.
- **Không bao giờ là lỗi.** Call thất bại (status `failed`, `{error}` của
  Codex, `isError`, hay AppError bọc fence — fence chỉ tính với tool DevKit
  (`isDevkitTool`), vì output của shell cũng có thể trông y vậy) giữ hàng
  failed của transcript; view chỉ thấy payload thành công.
- **Preview bị cắt (8 KiB) không parse được → không có payload**: transcript
  tải nguyên hàng (`transcript/toolCallDetail.ts`, một query TanStack mỗi call,
  dùng chung với "Show full output") rồi hỏi view lại. Stub 64 KiB của Codex
  cũng không có payload. Marker ảnh trang của hàng đã lưu
  (`transcript_slim.go`) không phải câu trả lời — câu trả lời nằm ở `content`.
- **Ảnh đọc từ `ToolResultInput.content`**, không từ payload (`pdf.viewPages`).
- **Kiểm shape đồng bộ trước khi chunk lazy tải**: renderer parse rồi mới
  `createElement(LazyCard, …)`, nên một node khác `null` là một card chắc chắn
  vẽ được. Transcript dựa vào đó để chọn card nào được đứng ngoài phần gập
  (`ToolResultCard.tsx` `resultCandidate`, tối đa 3 mỗi turn): view trả `null`
  thì không chiếm chỗ, call rơi về khối generic.
- **Card nằm trong error boundary.** Card ném lỗi khi render, hay chunk lazy
  tải hỏng, rơi về hàng / khối generic thay vì làm sập transcript. Card đã
  đứng sau phần gập thì trong phần gập call vẫn chỉ là một hàng.

- **Đăng ký ở module sở hữu tool**, trong file `manifest.ts` của module đó —
  giống hệt vị trí `agent.attach` được đăng ký trong `agenthub/manifest.ts`.
  Module Code Graph tự viết renderer cho `codegraph.getApiFlow`, không phải
  Agent Hub viết hộ nó.
- **Renderer trả về node**, không gọi side-effect ngay khi render. Hành động
  (nút "Try in API Client", "Reveal in Code Graph"...) chỉ được thực hiện qua
  `dispatchIntent`/`dispatchAttachIntent` đã có — không import thẳng
  bridge/action của module khác, đúng nguyên tắc "không import ruột module
  khác" của `cross-module.mdx`.
- **Không có ghi dữ liệu nào từ renderer.** Mọi thao tác người dùng bấm từ
  card (gửi request, mở file...) vẫn phải đi qua bridge + Capability Gateway
  của module đó, y hệt như khi người dùng bấm từ UI chính của module —
  renderer không phải đường tắt quyền.
- **Tool chưa có renderer, hoặc renderer trả về `null`** (rawOutput hỏng hay
  bị cắt giữa chừng mà nó không dựng nổi): `renderToolResult` trả `null`,
  `AgentToolCall` rơi về nhánh `ToolOutput` JSON như hiện tại — không vỡ UI,
  không có card rỗng, không cần sửa gì ở nơi gọi.

- **Renderer không tự bọc `Suspense`.** Card lazy có thể suspend; nơi gọi
  `renderToolResult` giữ boundary — `AgentToolCall` dùng `fallback={null}`,
  card hoạt động (bên dưới) dùng chính card "đang chạy" làm fallback để lúc
  chuyển sang kết quả không có khung trống.

### Tool hoạt động: card luôn hiện, kể cả khi đang chạy

`frontend/src/workbench/toolActivity.ts` — registry thứ hai, cùng khoá tên
(`createToolRegistry`) với `registerToolResultView`, dành cho các tool **thay
đổi** thứ gì đó (tạo board/task, commit, push, gửi request…). Tool chỉ đọc
không đăng ký gì ở đây. Module sở hữu tool khai báo trong `toolActivities.ts`
của nó, gọi từ `manifest.ts`:

```ts
registerToolActivity("tasks.board.create", {
  module: "tasks",
  running: "Creating board", done: "Created board", failed: "Couldn't create board",
  // rawInput khi đang chạy (chưa có id: chỉ label), rawOutput khi xong (có ref để Open)
  target: ({ rawInput, rawOutput, state }) => ({ label, detail, ref }),
  preload: () => import("./SomeResultCard"), // tải sẵn chunk card kết quả lúc tool đang chạy
});
```

- Trong transcript (`StepGroup` của `AgentTurn`), mỗi tool hoạt động thành một
  card **nằm ngoài phần gập**: dòng tóm tắt của run vẫn gập như cũ (và vẫn
  chứa đủ mọi bước, kể cả các tool này, để xem input/output thô), còn card
  luôn hiện dưới nó. Một run chỉ có một tool hoạt động vẫn có dòng tóm tắt —
  đó là đường tới call thô.
- Đang chạy: "Creating board… · Backend" (từ `rawInput`). Xong: card kết quả
  của module (nhận `heading` = động từ của activity, vd "Created task", thay
  cho danh từ "Task") hoặc card chung có nút Open (`<module>.reveal`, riêng
  API client là `api.reveal`). Lỗi: động từ `failed` màu danger.
- Mượt: card đang chạy và card kết quả cùng khung `FramedCard` (header + một
  dòng) nên đổi trạng thái không đẩy nội dung bên dưới; chỉ card sinh ra lúc
  agent đang làm mới có hiệu ứng (`.activity-enter`, tắt dưới reduced
  motion) — transcript được ảo hoá, card lịch sử mount lại khi cuộn phải đứng
  yên.
- `target` là khai báo "tool này tác động lên đối tượng nào" dùng chung: nút
  Open của card đọc nó, và panel theo dõi (sau này) cũng sẽ đọc nó.

Đã khai báo: `tasks.board.create`, `tasks.create/update/setFields/transition/
claim/release/archive/comment.add/createFromPlan`, `notes.create/update/delete`,
`git.commit/push/branch.create/checkout`, `api.send/sendAdhoc`.

### Mở beside từ card (một hành động, không phải cơ chế mới)

Card có thể thêm nút "Open" dùng đúng `dispatchIntent(name, ref, {placement:
"beside"})` đã có (Primitive 2 của `cross-module.mdx`) — không cần thêm
registry hay kiểu dữ liệu mới. Ví dụ thật: agent gọi `notes.create`, card
đọc `id`/`title` từ `rawOutput`, nút "Open" dispatch `notes.reveal` với
`placement: "beside"` — mở note đó cạnh conversation, y hệt luồng
"Tasks → Code Graph" đã mô tả trong ma trận điểm nối của `cross-module.mdx`.
Mở 1 lần theo yêu cầu của người dùng, không tự động.

## Theo dõi agent (Follow)

Bật/tắt **theo từng session** bằng chip "Follow" trên thanh của ô nhập (lưu ở
`stores/agentPins.following`, mặc định tắt). Không tự mở document hay split
group: mỗi thay đổi tự mở một group mới sẽ phá layout (nguyên tắc #3 của
`cross-module.mdx`), nên mọi thứ nằm ở một chỗ cố định.

- **Trong Agent Hub**: pane phải của chính module (`openPanel`, chỗ mà Agent
  panel đã nhường) hiện `AgentActivityPanel` (`modules/agenthub/follow.tsx`):
  feed các thay đổi của session, mới nhất trên cùng — card đang chạy, card kết
  quả, và lệnh terminal chạy lâu — rồi bên dưới là **bản xem trực tiếp** của
  đối tượng mới nhất mà module sở hữu vẽ được. Module khai báo bản xem bằng
  `registerEntityPreview(module, kind, render)` (`workbench/toolActivity.ts`);
  hiện có `tasks:task` (chính `TaskDetail` layout panel, tự cập nhật theo
  `tasks:changed`). Không có bản xem thì giữ card + Open. Panel tự đọc
  transcript từ store nên chỉ nhận một element mỗi session, không phải mỗi
  token. Chỉ tab đang hiện điều khiển pane: đổi tab là đổi session theo dõi,
  hoặc đóng nếu session đó không được theo dõi. Đóng pane = thôi theo dõi.
- **Ngoài Agent Hub** (Agent panel): không có pane để lấp, mỗi thay đổi xong là
  một toast kèm Open. Chỉ những thay đổi xong từ lúc bật — lịch sử không bắn
  lại thành loạt toast.

## Cách thể hiện trên UI

**Vị trí:** trong `AgentToolCall.tsx`, thay cho nhánh `content.map(...)` +
"Show full output" hiện tại (nơi đang rẽ theo `item.type === "diff" |
"terminal"`) — hai bên loại trừ nhau, không hiện cả hai cùng lúc. Chỉ tính
khi `state === "done"` (một call đang chạy chưa có `rawOutput` để render).
Card nằm trong cùng khối thu gọn/mở rộng như `ToolOutput` trước đây — không
tự mở, giống mọi hàng khác trong transcript. Nếu `call.truncated` và card
rơi về JSON vì `rawOutput` bị cắt, bấm "Show full output" tải nguyên hàng rồi
tự nâng cấp lên card mà không cần refresh.

Từ Phase 2, call xong có card còn **đứng sau phần gập** của run
(`transcript/ToolResultCard.tsx`): tối đa 3 mỗi turn theo thứ tự gọi, chỉ những
call mà view thật sự vẽ; phần còn lại là nút "+N more results in the work
above" mở phần gập ở bước ẩn đầu tiên. Trong phần gập, call vẫn là một hàng.

**Ví dụ cụ thể (đã triển khai):**

| Tool | Card | Hành động trên card |
| --- | --- | --- |
| `codegraph.getApiFlow` | Danh sách bước Controller → Service → Repository, rút gọn từ `rawOutput` | "Reveal in Code Graph" (`codegraph.reveal`, kind `endpoint`) |
| `codegraph.searchSymbol` | Danh sách symbol match, mỗi dòng tự bấm được | `codegraph.reveal` (kind `node`) trên từng dòng — không đăng ký gì mới |
| `codegraph.listEndpoints` | Danh sách endpoint, mỗi dòng tự bấm được | `codegraph.reveal` (kind `endpoint`) trên từng dòng |
| `api.fromEndpoint` | Method + URL của bản nháp, ghi chú về body (không hiện body — có thể chứa dữ liệu thật) | "Try in API Client" (`api.fromEndpoint` intent đã có sẵn) |
| `api.send` | Status code + thời gian + kích thước + cờ `truncated` (không hiện body — request đã gửi thật, khác bản nháp) | "Open" (`api.reveal`, mở request đã lưu) |
| `tasks.create` / `tasks.get` / `tasks.update` / `tasks.transition` | Key + title + status (một card dùng chung cho cả 4; `transition` trả `{task, verifying}` nên đọc task ở `task`) | "Open" (`tasks.reveal`) |
| `notes.create` / `notes.update` | Chỉ tiêu đề — không hiện `preview`/`body`, dữ liệu đã giải mã của note (ít lộ hơn cả JSON thô hôm nay, vốn đang hiện nguyên) | "Open" (`notes.reveal`) |
| `git.commit` | Short SHA + subject | "View diff" (`git.reveal`, kind `commit`, bằng SHA đầy đủ) |
| `git.diff` | Tên file đổi + số dòng (không phải toàn bộ diff — đã có `AgentToolDiff` cho điều đó) | "View diff" — chỉ hiện khi `rawInput.rev` khác rỗng; diff work tree không có view riêng để mở lại đúng những gì tool đã thấy (xem `git.reveal` trong `manifest.ts`) |
| `db.query` | SQL (dòng đầu) + `DataTable` 20 dòng đầu, "Show all"; lệnh ghi: "N rows affected" / "Done". Không có profile — kết quả không mang nó | "Copy CSV"; "Open in Database" (console "Agent query", không bao giờ chạy, không có với lệnh ghi) |
| `db.explain` | `PlanDiagram` khung cố định | "Open in Database" (nói khi console không cùng connection với agent) |
| `db.schema.get` / `db.listForeignKeys` | Schema → bảng (số cột), mở ra thấy cột; FK `table.column → ref.column`; gập ở 40 | — |
| `kafka.peekMessages` | `DataTable` Offset/Key/Value (≤ 120 ký tự)/Time; bấm dòng → giá trị đầy đủ dưới bảng | "Open in Kafka" (`kafka.reveal`) |
| `kafka.listTopics` / `describeTopic` / `listConsumerGroups` / `publishMessage` | Bảng gọn / dòng định nghĩa; publish: partition · offset · time | listTopics: bấm dòng mở topic; describe/publish: "Open in Kafka"; groups: không |
| `ssh.runCommand` | `$ command` + output mono, 20 dòng, "Show all"; bỏ escape ANSI khi hiện. Không có exit code (tool không trả) | "Copy" (byte gốc) |
| `pdf.viewPages` / `search` / `readText` / `info` / `list` | Ảnh trang (từ `content`; hàng đã tải lại: khung giữ tỉ lệ + ghi chú); hit có `<mark>`; text theo trang; dòng định nghĩa | Bấm ảnh → full size |
| `workspace.memory.*` | Card entry (kind, title, summary, body 6 dòng, revision) hoặc danh sách `[kind] title — summary` | — |

Kết quả tool không còn là "cả bản ghi": `workspace.memory.create|update|delete|restore`
trả entry không kèm `body` (card lấy body từ `rawInput`, `parseMemoryEntry(rawOutput, rawInput)`),
`tasks.*` trả task không kèm `history`/`description` (trừ `tasks.get`), `git.status` và
`agenthub.listPeers` trả dạng gọn. Mọi kết quả văn bản vượt `ResultBudget` (24 KB,
`internal/mcp/result_budget.go`) bị cắt ở ranh giới phần tử và có khoá `_truncated` — card đọc
phần còn lại như bình thường (`db.query` được đặt `truncated: true`). View mới không được đòi
một trường mà tool đã bỏ đi: thêm test shape cho cả dạng gọn.

Card `db.*`/`kafka.*`/`ssh.*` do module đó đăng ký (`modules/<module>/toolViews`),
`pdf.*` do Agent Hub (`agenthub/toolViews` — PDF thuộc về session),
`workspace.memory.*` do workbench (`workbench/registerViews.ts` — không module
nào sở hữu workspace memory).

**Hai intent mới cho Phase 2** (để Agent Hub mở bảng/topic mà không import
module kia):

- `database.reveal` — `{kind:"table", id:"schema.table", profileId?}` mở bảng
  trên `profileId` (qua đường chọn connection bình thường; profile lạ →
  `"unavailable"`; không có thì connection đang chọn). Schema có dấu chấm viết
  trong ngoặc kép SQL: `"sales.eu".orders`; thiếu schema → `"unavailable"`. Hoặc
  `{kind:"console", id: sql, label?}` mở console chứa câu lệnh, không chạy.
- `kafka.reveal` — `{kind:"topic", id}`: đưa Kafka lên màn hình trước, làm mới
  store từ Go, chờ tối đa 12 s rồi chọn topic; không có connection hay topic →
  `"unavailable"`.

**Cố tình chưa làm — dữ liệu lớn hoặc nhạy cảm, cần bàn phạm vi riêng:**
`codegraph.getBlastRadius`; `vault.*`, `accounts.*` (nhạy cảm); tool ghi/phá
hủy như `notes.delete`, `git.push` (giữ JSON thô để thấy đúng agent đã làm gì,
không tô vẽ).

**Nhất quán với cái đã có:** mọi card là một
[Framed card](/dev-kit/framed-card) — header (icon, tên, một sự kiện ngắn,
một hành động "mở ở chỗ khác") ôm lấy một preview lõm vào bằng khung 4px —
cài đặt duy nhất ở `frontend/src/components/ui/framed-card.tsx` (vùng chung
mọi module đã import, không phải trong `modules/agenthub`, để một renderer
module khác đăng ký không phải import ngược vào Agent Hub chỉ để dùng khung
card). Card đơn (`ApiFlow`, `Task`, `Note`, `GitCommit`, `Send`,
`EndpointDraft`) đặt hành động trên header; card danh sách mà mỗi dòng tự mở
được (`SymbolMatch`, `EndpointList`) không có hành động header, mỗi
`FramedCardRow` là một lối vào.

Thay cho thiết kế trước đó — `ToolResultRow`/`ToolResultList` dựng theo
`Agent / Row` (Figma page **17 Agent Hub**, frame
[`Agent / Tool Result`](https://www.figma.com/design/3dOzSZBYY7QtzANFTCfEe8/DevKit?node-id=1336-3174)).
Frame đó chưa được vẽ lại theo Framed card; xem mục Figma của trang Framed
card.

Một giá trị (SHA, method HTTP, id, status code) luôn ở `text-code-*` (Geist
Mono) — không viết như văn xuôi, đúng nguyên tắc "Geist Mono cho đường dẫn,
id, lệnh" của `design-system.mdx`.

**Trạng thái:** card kế thừa `state` (running/done/failed) từ `ToolCall`
giống hàng generic — đang chạy thì không có `rawOutput` để render nên vẫn
hiện shimmer "running…" như hôm nay; thất bại thì vẫn hiện `reason` inline
giống hàng generic, không cần renderer riêng xử lý lỗi.
