## 1. Synthesis

### 1.1 Top 14 rules for DevKit (ranked by expected payoff x evidence strength)

1. **Never depend on native scroll anchoring in WebKitGTK; keep one JS anchoring mechanism and turn the browser's off for the list.** Evidence: WebKit bug 298514 "Enable scroll anchoring" was only fixed in trunk on 2026-03-27 (commit 310113@main, no release named; Simon Fraser: the earlier implementation "has some issues with async scrolling"); the WebKitGTK 2.52.0 NEWS has no scroll-anchoring item; use-stick-to-bottom and virtua both avoid/disable `overflow-anchor` because they own anchoring (virtua README sample sets `overflowAnchor: "none"` on header/footer "because it will conflict with scroll anchoring of virtualizer"). Do: exactly one corrector (virtualizer item-size compensation OR your own `PrependAnchor`, never both plus the engine), set `overflow-anchor: none` on the scroller if a Chromium dev run shows double compensation. Verify: scripted prepend + above-viewport resize in MiniBrowser WebKitGTK and Chromium; assert `scrollTop` delta equals size delta, in both. Confidence: high on the facts, medium on "2.52 has no anchoring" (inferred from the absence in NEWS and the March-2026 trunk commit).
2. **Replace hand-rolled bottom-follow/prepend compensation with the virtualizer's own end-anchoring, or at minimum copy its contract.** TanStack's chat guide (current docs): `anchorTo: 'end'`, `followOnAppend: true`, `scrollEndThreshold: 80`, stable `getItemKey`, `measureElement`; "if the viewport is pinned to the end before the measured size changes" it adjusts by the size delta; appended items never pull a reader who scrolled up; no `column-reverse`, no manual `scrollTop += delta`. DevKit has virtual-core 3.17.7 installed (the options exist) but the transcript still carries custom anchor code. Do: spike `anchorTo:'end'` behind a flag on the transcript, keep the existing frame gate and "only user scroll-up unpins" rule. Verify: existing prepend/stream tests + a WebKitGTK scenario "stream 2,000 tokens while reader is pinned / 80 px up / 400 px up". Confidence: medium-high (doc is read; behaviour on WebKitGTK is not measured by anyone).
3. **Stream markdown by freezing settled blocks and re-rendering only the tail; make the tail's re-render at most once per frame (or 50 ms).** Evidence: Hermes-agent PR #67236 (self-reported, real Ink render): 1,024 blocks 333.5 s -> 21.6 s (15.4x), per-update cost ~flat at ~9 ms, "remaining per-append cost is layout of the growing tree, not parsing"; boundary rule = blank line outside code/math fence, an unmatched `$$` holds the boundary back; Streamdown memoizes per block and ships LRU caching; AI SDK `useChat` default renders on every chunk and documents `experimental_throttle: 50` (renamed `throttle`, stable, July 2026 per a release note, snippet). DevKit already did the parse side (3.07 ms for 20 kB in 1,000 chunks). Remaining gap: verify the React side (settled blocks keep element identity, code blocks do not re-highlight, the tail is the only block whose props change) with a Profiler "why did this render" check on a 300-block answer. Confidence: high.
4. **Estimate heights from content, learn from measurements, and cache by (id, width).** The scrollbar-drag worst case is a jump into unmeasured territory where every estimate is wrong and each late measurement triggers a correction. CM6 does exactly this: `HeightOracle` estimates per line from `lineLength`/`charWidth`/`lineHeight` and refines from measured samples (`heightSamples` at 0.1 px); Vaughn's react-window issue #6 states the structural problem ("aligning items correctly at list boundaries", "may be difficult to align the first cell with zero without introducing scroll janky"); TanStack ships `takeSnapshot()` + `initialMeasurementsCache` to restore measured sizes. Do: (a) per turn-kind running mean of measured heights as the estimate; (b) per-paragraph estimate from character count and container width (optionally Pretext, rule 12); (c) persist measured heights in a Map keyed `turnId + width bucket`, reuse after remount; (d) log estimate error `|est - measured|/measured` per kind in dev. Verify: error distribution before/after on the 1,000-turn fixture; scrollbar-drag test records `scrollTop` corrections per second. Confidence: medium-high (mechanism evidenced; the payoff size for DevKit is not).
5. **During a scrollbar drag or fast scroll, mount cheap shells, not real turns.** Evidence is indirect: Glide's FAQ ("Once you need to load/unload hundreds of DOM elements per frame nothing can save you"), VS Code terminal post ("hard cap imposed by the layout engine"; layout alone can exceed 16.6 ms), react-window article ("overscanning too many entries can affect performance negatively"), TanStack `isScrolling` + `isScrollingResetDelay` (150 ms) + optional `scrollend`. This is an INFERENCE (no source tests "shell during drag"): render turns whose index is newly entering during `isScrolling` as fixed-height skeletons with the estimated height, hydrate on settle (scrollend, or the 150 ms fallback). Keep overscan low while `isScrolling`. Verify: frameStall probe on a scripted full-range scrollbar drag in WebKitGTK; compare p90 frame gap and number of React commits. Confidence: low-medium (design inference).
6. **Opt every component that calls `useVirtualizer` out of React Compiler memoization (or verify the compiler already bails).** Issue #743: the compiler memoized `getVirtualItems()` and returned zero items; maintainer endorsed `'use no memo'` ("a reasonable temporary workaround", Dec 2024) and later closed with `directDomUpdates` as the fix (a commenter reported it did not work for them); bun/oxc lint rule `react-hooks/incompatible-library` lists `useVirtualizer` (snippet). DevKit has 4 callers, 0 directives. Do: add the directive or a test that renders the list, scrolls, and asserts mounted rows change; check the build output / compiler diagnostics. Confidence: high that the hazard exists, unknown whether the 1.0 compiler bails on these files automatically.
7. **Use `content-visibility: auto` only on coarse units, with `contain-intrinsic-size: auto <estimate>`, and never per small element on WebKit.** web.dev (Chrome 85, Firefox 125, Safari 18): 232 ms -> 30 ms render on its demo, `auto` keyword remembers last rendered size, off-screen content stays in the accessibility tree. Slate docs: in Safari, applying it to each element "is often slower than not using it at all"; the fix is chunking and applying it only on lowest-level chunks. Do: one `content-visibility` boundary per turn (or per run of tool cards) in the mounted window, not per code line/table row; measure in WebKitGTK 2.52 before widening. Confidence: high (docs), medium for WebKitGTK specifics (engine version support not verified; WebKitGTK 2.52.0 NEWS says nothing).
8. **Cut component and DOM count per transcript row and delegate events.** GitHub's diff v2 (Apr 3, 2026): 8 -> 2 components per diff line, single top-level handler using `data-*` instead of 20+ handlers per line, state moved down to conditionally rendered children, flat Map lookups; INP ~450 ms -> ~100 ms on a 10,000-line PR; virtualization for p95+ PRs: 10x less heap/DOM, INP 275-700+ ms -> 40-80 ms. DevKit has ~340 DOM nodes per mounted turn (2.7k / 8). Do: audit the heaviest turn kinds (tool card, diff, table) for components/handlers per element; delegate click/hover via `data-action` on the turn root. Verify: count nodes and listeners (DevTools) per kind; INP in frameStall. Confidence: high (primary, numbers).
9. **Highlight lazily and incrementally; never per token.** Tail code block stays plain until the fence closes (or highlight on a coarse timer); settled blocks highlight once, cached by (lang, content hash); prefer Shiki's JS regex engine in the browser (smaller, "faster for some languages", no big WASM; accuracy caveat: strict mode throws on unconvertible patterns). Editors: Lezer re-parses incrementally by reusing tree fragments; CM6 exposes `visibleRanges` so decorations skip off-screen text; VS Code stores tokens as `Uint32Array` (648 bytes -> 104 bytes -> 96 bytes for a 15-char line). Confidence: medium-high.
10. **One measure phase per frame; no layout reads in handlers.** CM6's contract (source-read): transactions "only write to the DOM"; reads happen in `requestMeasure` callbacks scheduled with rAF, same `key` replaces the previous request, many components share one read/write cycle, and it errors on re-entrant updates. Paul Irish's list of forcing APIs includes `scrollTop`/`scrollHeight`/`getBoundingClientRect`/`getComputedStyle` (some properties). ResizeObserver callbacks run after layout, before paint; a callback that changes size re-runs layout and can lose notifications ("loop completed with undelivered notifications", deferred to next frame, flash of broken layout). Do: put the follow-bottom write and the virtualizer measure in the same rAF; avoid `getComputedStyle` inside ResizeObserver callbacks (the transcript's `scrollMargin` effect does this on every resize). Confidence: high.
11. **Treat the xterm renderer as a decision, not a default.** xterm 6.0.0 removed the canvas renderer; only DOM and WebGL remain. DevKit uses DOM (no addon imported). VS Code measured 5-45x for canvas over DOM in 2017 under heavy output (below 10 FPS in DOM), but that code path no longer exists in xterm. Do: keep DOM until a streaming-output benchmark in WebKitGTK shows frame drops; if enabling `@xterm/addon-webgl`, feature-detect WebGL2, handle `onContextLoss` by disposing the addon (README's "suboptimal" approach) and falling back, and never rely on software WebGL (a Proxmox patch hit corrupted glyphs in Chrome software GL, SNIPPET). Confidence: medium.
12. **Spike DOM-free text measurement for height estimation (Pretext), prose only.** `@chenglou/pretext`: `prepare(text, font)` once, `layout(prepared, maxWidth, lineHeight)` returns `{height, lineCount}` with no DOM read; Intl.Segmenter + canvas `measureText`, cache by (segment, font); README warns `system-ui`/`-apple-system` unsafe on macOS, `text-wrap: balance/pretty`, `hyphens:auto`, `word-spacing`, variable fonts differ, needs `clearCache()` after web fonts load, bidi unsupported; launch-era claim ~0.09 ms for 500 paragraphs (secondary, unverified) and "up to 500x" (secondary). TanStack has a "pretext example" branch (listing seen in search; the page 403'd). Do: spike inside `estimateTurnSize` for text-only turns behind a flag; keep real measurement as the source of truth. Verify: estimate error histogram vs current heuristic, on Linux fonts used by DevKit. Confidence: medium-low (young library, README read, accuracy not independently measured).
13. **Editors: stay on viewport-DOM engines and bound what the viewport can become.** CM6 renders the viewport plus a margin (source: `VP.Margin = 1000` px, `MaxDOMHeight = 7e6` px with a height scaler beyond that, line-gap logic for very long lines) and warns long unwrapped lines or folds "can still make the viewport rather huge". Plate/Slate: under ~1,000 blocks no special work; above, enable chunking (`editor.getChunkSize` 1000, up to "10x"), apply `content-visibility` to lowest chunks only, keep `decorate/renderElement/renderLeaf/renderChunk` referentially stable, subscribe with selectors returning primitives. Plate 53.0.7 (June 2, 2026) "improve large document editing"; DevKit is on 53.3.3. Confidence: medium-high.
14. **Benchmark honestly.** The svelte-markdown PR #396 author retracted a "4.5-9x faster" claim because the benchmark only timed a deferred prop write (SNIPPET); Hermes isolates each strategy in its own process; Figma-style "p50 and p90, not mean" is already in smoothness.mdx. Do: every perf PR in this area reports commits, DOM nodes, long frames (p90 frame gap) on WebKitGTK, not only parse milliseconds. Confidence: high (process rule).

### 1.2 Decision note: when canvas/GPU rendering is justified vs optimized DOM

Evidence read:
- Canvas/GPU won where cells are uniform, content is machine-generated text and interaction is bounded: VS Code terminal (5-45x, DOM below 10 FPS under streaming; "hard cap imposed by the layout engine"), Glide Data Grid ("hundreds of DOM elements per frame" is the wall; millions of rows), Zed (a full custom UI framework, one instanced draw call per primitive type, design target 8.33 ms/frame; no measured frame times published), Figma (WebGL then WebGPU; gains "on some classes of devices", neutral elsewhere, hitches on backend swap, async readback/device loss complexity).
- Canvas costs that the sources themselves state: selection must be reimplemented (VS Code terminal post: DOM selection could not span off-screen content), accessibility needs a parallel structure (Google says AT "will not be impacted" for Docs but also that Chrome extensions depending on DOM broke; Glide: "none of the primary developers are accessibility users so there are likely flaws"), find-in-page disappears, text shaping/shaping consistency is on you (Zed uses OS shaping APIs), fallback paths (Figma blocklists devices by fallback rate; xterm WebGL has context loss), and a two-renderer maintenance burden (Figma had to translate shaders GLSL->WGSL to keep both).
- Teams that stayed DOM at huge scale got big wins from DOM discipline: GitHub (10,000-line diffs, 400,000+ DOM nodes worst case -> 10x fewer with virtualization, INP 450 -> 100 ms by cutting components/handlers), VS Code editor (viewport lines injected as one batched `innerHTML` string in `viewLayer.ts`), CodeMirror 6 (viewport DOM + height map), Monaco (design doc: "View elements here are actually HTML DOM nodes").
- Inference for DevKit (flagged as such): 
  - **Transcript: stay DOM.** It is rich, selectable, searchable, linkable, accessible prose with interactive cards; canvas would forfeit native selection, find, copy, links, IME. Gains must come from fewer nodes, stable anchoring, frozen blocks.
  - **Data grids (10k x 30):** optimized DOM windowing first: row buffer small, column virtualization (AG Grid renders no column buffer, 10 rows above/below by default, 500-row cap), fixed row height, no per-cell React component if avoidable. Move to canvas only if, after that, a scripted full-range drag still drops frames in WebKitGTK and the grid's features are bounded (no rich cells). If so, copy Glide's accessibility caveat and keep a hidden semantic fallback.
  - **Terminal:** the only "canvas-class" option left is xterm WebGL; decide by measurement (rule 11).
  - **Code editors:** CM6 DOM is the evidence-backed choice; VS Code ships a GPU editor-rendering option in `viewLines.ts` (`useGpu` flag seen in source; release-note details NOT verified), which says even VS Code treats GPU as an opt-in layer over DOM.
  - **React Flow canvases:** not researched here (outside the sources read).
- Rule of thumb that the evidence supports: go canvas only when (a) the per-frame DOM work you cannot avoid is in the hundreds of elements AND remains after virtualization/containment, (b) content is uniform and non-rich, (c) you can afford to reimplement selection, find and a11y, and (d) you can measure on the weakest engine (WebKitGTK).

## 2. Virtualization libraries and scroll stability

### A1. TanStack Virtual: Virtualizer API reference
- Author/role: TanStack team (Tanner Linsley and maintainers). URL: https://tanstack.com/virtual/latest/docs/api/virtualizer. Date: current docs, fetched 2026-10-21. READ.
- Claims: `overscan` default 1 ("number of items to render above and below"); `estimateSize` should return an estimate when measuring dynamically and docs recommend estimating the largest reasonable size "to get better initial positions"; `getItemKey` default is the index, "override this when possible to return a unique identifier", memoize it; `shouldAdjustScrollPositionOnItemSizeChange` (instance property): by default corrections are skipped while the user scrolls backward; `isScrollingResetDelay` default 150 ms (fallback where `scrollend` is not uniform), `useScrollendEvent` default false; `useAnimationFrameWithResizeObserver` default false and docs advise against enabling ("adds roughly one frame of delay and gives no batching benefit"); `initialMeasurementsCache`/`takeSnapshot()` restore measured sizes after navigation; `resizeItem` must not be mixed with `measureElement` on the same index; `anchorTo`, `followOnAppend` exist.
- Rule for DevKit: use `getItemKey`=turn id (already), pass a content-based `estimateSize` (rule 4), keep `useAnimationFrameWithResizeObserver` off, snapshot/restore measurements on tab switch instead of re-estimating. Verify by diffing `scrollTop` corrections with/without `takeSnapshot` after a tab round-trip.
- Caveats: docs describe behavior, no benchmarks; some options (e.g. `directDomUpdates`) are NOT in this page though a maintainer cites it elsewhere. Confidence: high.

### A2. TanStack Virtual: Chat guide
- Author: TanStack team. URL: https://tanstack.com/virtual/latest/docs/chat. Date: current docs. READ.
- Claims: example config `estimateSize: () => 72`, `anchorTo: 'end'`, `followOnAppend: true`, `scrollEndThreshold: 80`, `overscan: 6`; prepend is stable because the visible item is captured before the data change and matched by key afterwards ("Do not use index keys for chat history"); streaming growth: "if the viewport is pinned to the end before the measured size changes" the virtualizer "adjusts by the size delta"; "You do not need `flex-direction: column-reverse`, inverted transforms, or manual `scrollTop += delta`"; show "Jump to latest" using `isAtEnd()`; `scrollToEnd()` after mount in `useLayoutEffect`.
- Rule: evaluate replacing DevKit's own prepend anchor/bottom-pin with these options (synthesis rule 2). Avoid `column-reverse` (also breaks selection order/keyboard behavior; the guide itself rejects it).
- Caveats: new API; no WebKitGTK evidence; threshold 80 is an example (no default stated). Confidence: medium-high.

### A3. "TanStack Virtual just got a lot faster, and finally handles iOS"
- Author: Tanner Linsley (TanStack creator). URL: https://old.tanstack.com/blog/tanstack-virtual-perf-and-ios. Date: 2026-05-19. READ.
- Claims (author-reported): `resizeItem` copied the whole size Map to invalidate a memo: "the worst one", 10k-item `resizeItem` storm 1.9 s -> 1.3 ms; cold mount 100k real React 6.1 -> 4.5 ms; `setOptions` x10,000 14.4 -> 1.3 ms; flat `Float64Array` for start/size with lazily built `VirtualItem` objects; iOS: "iOS WebKit treats any programmatic scrollTop write during a touch-driven scroll as a cancel instruction", so writes are deferred during touch + 150 ms post-touchend + bounce and flushed once; scroll adjustment is direction-gated (backward scroll skips corrections by default; restore via `shouldAdjustScrollPositionOnItemSizeChange`); `takeSnapshot()` added; still open: reverse infinite scroll, Fenwick tree for 1M+.
- Rule: upgrade benefits are real (our installed core 3.17.7 includes them). Do not write `scrollTop` from our own code during an active touch/wheel inertia on WebKit. Note the default "backward scroll skips above-viewport corrections" means upward drags near unmeasured turns show drift by design: test it, do not assume stability.
- Caveats: author-reported micro-benchmarks on his own harness; the iOS logic is touch-specific, DevKit on Linux desktop uses wheel/scrollbar (touchpad on WebKitGTK is not the same path). Confidence: medium.

### A4. TanStack/virtual issue #1250 (iOS deferral for programmatic scrolls)
- Author: fidalgodev (reporter); piecyk (maintainer). URL: https://github.com/TanStack/virtual/issues/1250. Opened 2026-08-03, closed 2026-10-13 via PR #1318. READ.
- Claims: `isScrolling` is set by any scroll event including the library's own programmatic writes, so on iOS WebKit "programmatic landings ... have their measurement corrections deferred past a paint"; reproduced in Playwright WebKit iPhone 13 profile: 4.0 px transient offset vs 0.8 px without deferral; fix commits "defer iOS scroll corrections only for touch-driven…" (Oct 13) and "catch late taps on a fling…" (Oct 14); versions tested 3.17.6/3.17.7.
- Rule: bump `@tanstack/react-virtual`/virtual-core when the release after 3.17.7 is published if any WebKit scrollToIndex flicker is seen; add a "scrollToIndex lands within 1 px after 2 frames" check on WebKit.
- Caveats: iOS-specific path; shows the library is actively fixing WebKit-only landing glitches, i.e. WebKit differences are a live risk class. Confidence: high (facts), low for relevance to WebKitGTK.

### A5. TanStack/virtual issue #743 (React 19 / React Compiler returns zero items)
- Author: community reporters; maintainer piecyk. URL: https://github.com/TanStack/virtual/issues/743. Opened 2024-06-27, closed 2026-06-02. READ.
- Claims: the compiler memoized `getVirtualItems()` so it did not reflect later scroll updates; workarounds: virtualizer in a `useRef` (worked for one user, not another), `'use no memo'` (maintainer: "a reasonable temporary workaround", 2024-12-12), a `useNoMemo` wrapper around only `getVirtualItems()` (confirmed by several, including 2026-05-28), `directDomUpdates: true` (maintainer's closing fix; a user reported on 2026-07-19 that it did not work for them).
- Rule: synthesis rule 6. Add `"use no memo"` to the 4 callers or prove via a scroll test that they re-render.
- Caveats: the lint rule evidence (bun/oxc `incompatible-library`) is SNIPPET-only; React Compiler 1.0 behaviour for this hook not verified here. Confidence: high (hazard), medium (applicability).

### A6. WebKit Bugzilla 298514 "Enable scroll anchoring"
- Author: karesz.carco (reporter), Simon Fraser (WebKit, assignee). URL: https://bugs.webkit.org/show_bug.cgi?id=298514. Reported 2025-09-07, RESOLVED FIXED 2026-03-27 (commit 310113@main, PR #61508); fixed-in release not stated. READ.
- Claims: Safari jumps when DOM height above the viewport shrinks, Chrome/Firefox/Edge do not (`overflow-anchor`); `overflow-anchor: none` had "no effect in Safari stable"; Fraser: "We have an implementation, but it has some issues with async scrolling."
- Rule: on WebKitGTK 2.52 assume no engine anchoring; own it in JS (synthesis rule 1). Re-test after each WebKitGTK bump; when anchoring arrives it could double-compensate.
- Caveats: Safari 18 report; MDN (fetched) marks `overflow-anchor` "Baseline 2026, newly available since September 2026" but the Safari row was truncated, so I cannot say which WebKit/WebKitGTK release carries it. WebKitGTK 2.52.0 NEWS (READ, 2026) lists only touch-scroll smoothing, "scrollend" emission after scroll animations, "several crashes and rendering issues". Confidence: high (bug facts), medium (what it means for 2.52).

### A7. virtua README
- Author: inokawa (maintainer). URL: https://github.com/inokawa/virtua (README fetched raw to scratchpad). Date: current. READ.
- Claims: "Zero-config virtualization ... dynamic size measurement, scroll position adjustment while reverse scrolling and imperative scrolling, iOS support"; goals include reducing "synchronous layout recalculation", "visual jumps on repaint"; ~3 kB gzipped; ResizeObserver is required; items jump when content inside renders late (images, components that render after mount) and again each remount; fixes: reserve space with explicit dimensions/`aspect-ratio`, or `keepMounted`; sample sets `overflowAnchor: "none"` on header/footer "because it will conflict with scroll anchoring of virtualizer"; comparison table marks reverse scroll in iOS Safari "user must release scroll" (issue #473); "Benchmark: WIP".
- Rule: late-resizing content (images, mermaid/diagram blocks, lazy code highlight, tool-card expansion) is the main source of above-viewport corrections: give every async element a reserved height (aspect-ratio for images; fixed min-height for diagrams) and let a collapsed card be a fixed height until expanded by the user. Verify by counting size-change events per mounted turn after first paint.
- Caveats: author's own comparison table, no published numbers. Confidence: medium.

### A8. react-window README (current)
- Author: Brian Vaughn (maintainer). URL: https://github.com/bvaughn/react-window. Date: current. READ.
- Claims: dynamic row heights via `useDynamicRowHeight`: "Dynamic row heights are not as efficient as predetermined sizes"; `Grid` cell sizes "must be known ahead of time"; `rowKey`/`columnKey` must be `useCallback`'d, "do not use an inline function"; `overscanCount` is a plain extra-rows count.
- Rule: a grid with known column widths and fixed row height is the cheap case; keep data-grid row height fixed (smoothness.mdx 3.1 already says it) and column widths known.
- Caveats: README never describes internals; the page does not distinguish versions. Confidence: medium.

### A9. react-window issue #6 "Support just-in-time measured content"
- Author: Brian Vaughn (react-window/react-virtualized author, ex-React team). URL: https://github.com/bvaughn/react-window/issues/6. Opened 2018-05-30, closed 2024-08-13 (as completed, likely stale bot per a comment). READ.
- Claims: measurement constraints for a CellMeasurer-style design: measured only if no measurement exists, resets must be imperative, and "Cells at a given index can only be positioned after all cells before that index have been measured"; removing the third constraint (random access with an `estimatedItemSize`) "would make react-window much more performant for use cases like chat applications"; the hard part: "aligning items correctly at list boundaries" and aligning the first cell with offset 0 "without introducing scroll janky". 1.0.0 shipped without the feature (2018-07-22).
- Rule: this is the root of every estimated-size virtualizer (TanStack, virtua, CM6 height map): random access needs estimates; any estimate error shows as scrollbar-thumb jump and an end-of-list/start-of-list alignment correction. Design for it (rule 4).
- Caveats: 2018 design discussion; v2 of react-window has dynamic rows now (README). Confidence: high.

### A10. "Virtualize large lists with react-window" (web.dev)
- Authors: Jason Miller and Houssein Djirdeh. URL: https://web.dev/articles/virtualize-long-lists-react-window. Last updated 2019-04-29. READ.
- Claims: infinite loading "can lead to an excessively large DOM size"; windowing "improves both the rendering and scrolling performance"; rows are absolutely positioned and recycled; `overscanCount` default 1; "overscanning too many entries can affect performance negatively"; profile with Chrome FPS meter before virtualizing.
- Rule: keep overscan minimal (DevKit uses `TRANSCRIPT_OVERSCAN`/`TRANSCRIPT_HEAVY_OVERSCAN`; measure whether each extra mounted turn is paid for on WebKitGTK).
- Caveats: 2019, react-window v1, no numbers, no variable-height treatment. Confidence: medium (generic).

- Rule: native scrolling container + canvas drawing is how to keep scrollbar behavior native while avoiding DOM churn (a hidden sizer element gives the scrollbar); cell text selection/copy and find are features the app re-adds. Consider only if the 10k x 30 DOM grid fails (decision note).
- Caveats: vendor claims; a11y is self-described as likely flawed. Confidence: medium.

### D5. AG Grid: DOM virtualisation
- Author: AG Grid (Ag Grid Ltd) docs team. URL: https://www.ag-grid.com/javascript-data-grid/dom-virtualisation/. Date: current docs. READ.
- Claims: rows and columns are both virtualised; row buffer default 10 above and 10 below (a pixel range = `rowBuffer` x default row height, 420 px each side at a 42 px default; taller rows -> fewer rows in the buffer); `rowBuffer=0` turns it off; max rendered rows cap 500 (crash safeguard, `suppressMaxRenderedRowRestriction` lifts it); "There is no column buffer - no additional columns are rendered apart from the visible set" because horizontal scrolling is less CPU intensive than vertical; `suppressRowVirtualisation` removes buffering (example: 900 cells rendered up front).
- Rule: a mature DOM grid at scale uses no column overscan and a small row buffer; DevKit's grids should set row overscan by pixels, not count, and use zero column overscan; confirm the DevKit table windowing (`useVirtualRows` pads with spacer `<tr>`) has a matching cap and works with sticky headers (it does per smoothness.mdx 6.3).
- Caveats: no numbers on frame times; "less CPU intensive" is stated, not measured. Confidence: medium.

### E1. Google Docs: "Updating the way Google Docs renders documents" (canvas-based rendering)
- Author: Google Workspace Updates blog (author not stated). URL: https://workspaceupdates.googleblog.com/2021/05/Google-Docs-Canvas-Based-Rendering-Update.html. Date: 2021-05-11 (updated 2021-05-26). READ.

- Caveats: no numbers published; secondary commentary (The New Stack, Hacker News via search) raised accessibility doubts and skepticism about JS beating native layout (SNIPPET). Confidence: high (facts), n/a (no data).

### E2. "Figma rendering: Powered by WebGPU"

### E3. "The uphill climb of making diff lines performant" (GitHub)
- Authors: Luke Ghenco and Adam Shwert (GitHub senior software engineers). URL: https://github.blog/engineering/architecture-optimization/the-uphill-climb-of-making-diff-lines-performant/. Date: 2026-04-03. READ.

### F1. "content-visibility: the new CSS property that boosts your rendering performance"
- Authors: Una Kravets, Jeremy Wagner, Vladimir Levin (web.dev). URL: https://web.dev/articles/content-visibility. Published 2020-08-05, updated 2025-09-23. READ.
- Claims: 232 ms -> 30 ms initial render (7x) with `content-visibility: auto` on story sections; expected "50% or more" rendering reduction; `contain-intrinsic-size` is "a placeholder size in lieu of rendered content" and without it an off-screen section is 0 px so "the size of the scrollbar will shift"; `contain-intrinsic-size: auto 300px` remembers the last rendered size; the content stays searchable and in the accessibility tree (use `aria-hidden` for landmarks); Facebook's `content-visibility: hidden` experiment: up to 250 ms faster navigation back to cached views; support: Chrome 85, Edge 85, Firefox 125, Safari 18 ("Baseline Newly available" as of 2025-09-15).
- Rule: use `contain-intrinsic-size: auto <estimate>` so remembered sizes stabilize the scrollbar; do not combine with a virtualizer that also positions by measured size on the same element without checking they agree (two systems owning the same height).
- Caveats: Chrome-measured demo; engine support in WebKitGTK 2.52 not confirmed (no NEWS item). Confidence: high (doc), medium (applicability).

### F2. MDN: `overflow-anchor` and "Overview of scroll anchoring"
- Author: MDN contributors. URLs: https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor and https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor/Guide_to_scroll_anchoring. Date: current. READ (first 100k chars of each; the browser-compat table was truncated).
- Claims: scroll anchoring "adjusts the scroll position to compensate for the changes outside of the viewport"; on by default where supported; suppression triggers on the anchor node or an ancestor: computed value changes of `top/left/right/bottom`, `margin`/`padding`, any width/height property, `transform`/`translate`/`scale`/`rotate`; "`position` changes anywhere inside the scroll container also disable scroll anchoring"; values `auto`/`none`; an opted-out area cannot be opted back in by a descendant; if a page misbehaves it is probably because "some `scroll` event listener is not handling the extra scrolling to compensate for the anchor node movement"; page states it is Baseline 2026 "since September 2026".
- Rule: a virtualizer that positions rows with `transform: translateY(...)` on each row is on the suppression list for those anchor candidates, so native anchoring mostly will not help a transform-positioned virtual list even in engines that support it; DevKit's rows use `transform: translateY` (`TranscriptStream.tsx` line ~647). Keep JS anchoring regardless.
- Caveats: the "virtualized/chat" paragraphs in the fetch result were the summarizer's general knowledge, not MDN content, and are not used. Confidence: medium-high.

### F3. MDN: ResizeObserver (processing model and loop error)
- Author: MDN contributors. URL: https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver. Date: current. READ.
- Claims: "Implementations following the specification invoke resize events before paint"; if a callback changes sizes, style and layout are re-evaluated and more events may fire; only deeper elements are processed per iteration, others "are deferred to the next paint, and an error event is fired on the `Window`"; the error "ResizeObserver loop completed with undelivered notifications" "only prevents user-agent lockup, not the infinite loop itself"; "visitors may see a flash of broken layout, as a sequence of changes expected to happen in a single frame is instead happening over multiple frames"; fix patterns: defer the resize write to `requestAnimationFrame`, or track expected sizes to stop the loop.
- Rule: never size an element A from a ResizeObserver on its descendant B in the same callback if A's size feeds B; measure with `borderBoxSize` entries (no `getBoundingClientRect`) inside the observer; when the virtualizer's `measureElement` changes the container height and the container is also observed, you get this loop: keep one observer per concern. virtua documents that the error can be ignored/filtered.
- Caveats: MDN sample uses `contentBoxSize`; `borderBoxSize` is documented on the entry page (not fetched). Confidence: high.

### F4. "What forces layout/reflow" (Paul Irish gist)
- Author: Paul Irish (Chrome DevTools/DevRel, later Google). URL: https://gist.github.com/paulirish/5d52fb081b3570c81e3a. Date: gist maintained to 2018+ (comments into 2025). READ.
- Claims: forcing APIs include `offsetWidth/Height/Top/Left`, `clientWidth/Height`, `getBoundingClientRect()`, `scrollTop/scrollLeft` (read and write), `scrollWidth/Height`, `scrollIntoView()`, `scrollTo/By()`, `focus()`, `innerText`, `window.scrollX/Y/innerHeight/innerWidth`, `elementFromPoint()`, `input.select()`, `getComputedStyle()` for some properties (height/width, top/right/bottom/left, margin/padding if fixed, transform, grid-template) or in shadow trees; "Read/write loops that force layout while changing the DOM are the worst case"; "Read metrics at the start of a frame, when values still match the last layout"; data from Blink, "WebKit is described as mostly consistent". Canvas 2D: a comment says `fillText()`/`strokeText()` force reflow in all browsers (comment-level claim).
- Rule: any code in the scroll/stream path reading `scrollHeight`/`scrollTop` after writing DOM is a forced layout; the virtualizer reads `scrollTop` itself, so our own code should read once per frame and reuse. `Range.getBoundingClientRect()` (used by selection/anchor code) also forces layout.
- Caveats: Blink-derived; one comment says `window.innerHeight` does not force layout in Chromium 133. Confidence: medium-high.

### F5. "Improving scroll performance with passive event listeners" (Chrome)
- Author: Kayce Basques (Chrome DevRel). URL: https://developer.chrome.com/blog/passive-event-listeners. Date: 2016-06-05 (Chrome 51). READ.
- Claims: passive listeners "provide a major potential boost to scroll performance, especially on mobile"; "Many times when you encounter scroll jank, the culprit is a touch event listener"; "The basic `scroll` event cannot be canceled, so it does not need to be set passive"; "prevent expensive work from being completed in the handler". No numbers.
- Rule: wheel/touchstart/touchmove listeners the app adds (e.g. user-intent detection that unpins follow-bottom) must be `{passive: true}`; a non-passive `wheel` handler blocks the compositor on engines that thread scrolling. Verify with a lint rule or grep for `addEventListener("wheel"`.
- Caveats: 2016; the claim that handlers block even without `preventDefault()` comes from web.dev article F6. WebKitGTK threaded-scrolling behavior not measured (Fedora's summary of 2.50-2.52 notes improved async scrolling "when main thread is busy", SNIPPET). Confidence: medium.

### F6. "Debounce your input handlers" (web.dev)
- Author: Paul Lewis (Chrome DevRel). URL: https://web.dev/articles/debounce-your-input-handlers. Date: last updated 2015-03-20. READ.
- Claims: input handlers "can block frames from completing"; touch/scroll handlers make the compositor wait ("stuttering and missed frames") even if they never call `preventDefault()`; recommended pattern: store event values in the handler, do visual changes once in a `requestAnimationFrame` callback guarded by a flag; reading visual properties in the rAF after style writes in the handler forces layout. No numbers.
- Rule: scroll handlers store only; one rAF reads and writes (matches DevKit's "frame gate"); do not call `setState` in a scroll handler. Prefer IntersectionObserver for visibility ticks (already done) and the virtualizer's own scroll subscription for offsets.
- Caveats: 2015, qualitative. Confidence: medium.

### F7. Pretext README (`@chenglou/pretext`)
