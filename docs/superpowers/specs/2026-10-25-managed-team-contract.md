# Managed team contract (TEAM1)

Date: 2026-10-25. Status: implementation contract for the first managed-team foundation; later phases below are requirements, not claims that those features exist. Local tracking references: `OPT-76c3b6` (TEAM1 contract), `OPT-12698e` (ledger), and `OPT-400ff3` (baseline). Task progress is tracked on the board; implementation/validation status is recorded in the managed-team implementation plan.

This reconciles the approved TEAM1 decisions in [TEAM1 contracts](2026-10-25-team1-contracts.md) with the current repository. It preserves Agent Hub/Tasks ownership and their existing gates. The managed workflow is opt-in, local to one workspace, and records execution metadata; Tasks remains the source of task content and status. It extends the existing `internal/agentwork` stdlib-only leaf and existing peer delivery substrate. It adds no runtime, task board, scheduler framework, second ledger/outbox, or parallel `internal/workgroup` package. Later phases below are requirements, not claims that their capabilities exist.

## 1. Ownership and package boundary

Storage owns migrations 49–50 and the persistence API (`CreateWorkGroup`, `UpdateGroupPolicy` CAS, `CreateWorkItem`, `BeginAttempt` CAS, `TransitionAttempt` CAS, bounded list pages, and `MarkAttemptAmbiguous` CAS). `internal/agentwork` owns shared stdlib-only DTOs, transition validation, scope validation, and the versioned requirements digest; it must not import `agenthub`, `tasks`, `git`, `storage`, `bridge`, `mcp`, `app`, or crypto implementations. The host must reconcile the selected session/turn before calling `MarkAttemptAmbiguous`; the method changes only that attempt and never replays. Tasks owns board records and terminal transitions; Agent Hub owns sessions, prompt delivery, stop state, and interaction queues; the existing gateway/tool path enforces capabilities and confirmation; React is a read/action client, never an authority. The persistence API is internal storage plumbing. Batch 2 adds the injected `agentwork.ManagedService` and real app composition, including scoped UI-identity checks and a conservative Tasks terminal guard; it still exposes no public managed API, UI feature or dispatch capability.

Do not create a second generic task-to-child handoff service. Reuse the B7 `agentwork` handoff and B5 durable peer outbox. Managed event payloads and consumers are distinct from peer chat, but use the existing durable delivery substrate and its dedupe/reconciliation behavior. Managed results are written to the ledger; chat text is not the source of truth.

## 2. Persisted contract

Migration 49 creates local, non-synced metadata tables for groups, work items, and attempts. Migration 50 adds explicit per-group status maps, independently versioned records, tombstones and live task uniqueness. Payload/artifact storage and event inbox remain later-phase additions. Names may follow the storage package's naming convention; these logical records and constraints are required:

| Record | Required fields and constraints |
|---|---|
| `agent_work_groups` | Opaque `id`; `workspace_id`, `board_id`, `parent_task_id`, required `coordinator_id`; `enabled`, `paused`; `policy_revision`; monotonic `revision`; created/updated timestamps. New groups default disabled and paused. Workspace/board/task scope is immutable after creation; re-scope is a new group or explicit audited operation. |
| `agent_work_items` | Opaque `id`; group/workspace/board/parent/task IDs; `role`; execution `state`; explicit task and requirements revisions; nullable current attempt ID; record revision; timestamps. Composite scope foreign keys prevent a row from referencing an item outside its group, and a deferred composite FK binds the current attempt pointer back to an attempt with matching scope. The pointer remains pinned after an attempt ends. |
| `agent_work_attempts` | Opaque `id`; work-item/group/workspace/board/parent IDs; optional `session_id`; role; state and dispatch step; task/requirements revision; monotonically increasing `generation`; attempt record revision; timestamps. Attempts are append-only in identity: retries create a new attempt. Lease, branch, verified revision, stop details, and result/evidence belong to later-phase extensions, not migration 49. |

Enforce composite scope foreign keys, unique attempt generation per work item, and compare-and-swap on every mutable group's/work item's/attempt's `revision`. Use opaque IDs generated by the host. Do not add prompt, evidence, path, artifact-body, task-description, transcript, secret, or permission/question-body columns. The foundation stores metadata only. If a later phase adds payloads/artifacts, it must use the existing vault codec, opaque references and the quota/retention policy below; it must not add plaintext columns.

## 3. Scope, authorization, and confidentiality

Every service request is derived from authenticated caller identity and server-side workspace/session grants. The host resolves group, board, task, session, folder, and repository IDs; it rejects mismatched workspace, board, parent task, current owner, or session. UI-supplied role, coordinator identity, grants, arbitrary paths, model choice, and “verified” flags are not authority. A child cannot self-assign, accept its result, release another writer's lease, expand scope, or bypass a Task transition gate.

Before create/dispatch/read-artifact/accept, re-check capability and current scope at the owning service. Task writes use Tasks APIs; session creation/prompt delivery/stop use Agent Hub APIs; worktree and branch use existing guarded Git APIs. A group opt-in does not grant unattended actions. D1's finite approval remains exact `db.query` only; every other gated operation uses its current gate/policy and asks or fails closed when its prompt handler is absent, server mode is active, or environment confirmation is required. No operation inherits approval from another operation.

Migration 49 stores no payload bodies. If a later phase persists briefs, checkpoints, result summaries, findings, or artifact bodies, encrypt them with the existing vault codec and bind as associated data to record ID, workspace, payload kind, and schema version. Verify binding and caller scope before decrypting. Vault locked means no payload dispatch/read; metadata can show a locked/waiting state. Do not write plaintext to logs, audit metadata, SQLite, temp files, tool descriptions, or event deltas. Audit records contain actor/session IDs, operation, revision, outcome/error code, and time only. Existing vendor transcripts and source files retain their existing storage contracts; this contract does not promise to encrypt them anew.

Treat all task text, results, artifacts, peer messages, and model output as untrusted data. They cannot change instructions, scope, grants, approvals, or verified provenance.

## 4. Revisions, CAS, leases, and acceptance

Requirements digest v2 is computed over host-resolved workspace/board/task identity, task description (which carries acceptance criteria), sorted `blockedBy` task IDs, folder scope, and the task branch field. Editing title, status, progress, comments, evidence, or result revisions does not change it. Legacy title, role-contract, separate-acceptance, and dependency-input fields may remain in the Go snapshot for source compatibility, but v2 ignores them. Dependency-input bindings belong in later immutable context/result records, not in the task requirements hash. Do not use `updatedAt` as a CAS token. The v2 prefix intentionally makes prior v1 snapshots reconcile; no old digest is silently accepted as current.

Progress, heartbeat, and appended evidence do not change requirements revision. A change to any v2 input increments the revision and makes old packages/results stale. Recompute from the current host snapshot at use; caller-supplied digests are not authority.

Review and integration begin as proposals. Auto-dispatch of reviewer and repair rounds requires
the person's per-group opt-in, and repair is capped at two rounds. Integration never starts
automatically; push and merge keep their existing gates.

All mutable group/item/attempt transitions include `expected_revision`; the store performs an atomic compare-and-swap and returns a stale-revision conflict without side effects. Each new attempt carries an increasing generation. Once execution integrations exist, every heartbeat, result write, and state transition must check `(attempt_id, generation, expected_revision)` against the current work-item pointer; old generations may append historical evidence but cannot mutate current state, dispatch, wake a coordinator, or accept work. Migration 49 does not yet provide a lease. Lease expiry alone must never prove that the old writer stopped. Reassignment requires host-confirmed process stop or isolated old workspace; otherwise mark blocked and require a human.

One active implementation writer per task/worktree. Migration 49's `current_attempt_id` permits at most one active attempt per work item; scheduler integrations must additionally enforce one writer per task/worktree before dispatch. Reviewer and integrator are separate work items with separate session/branch ownership. A later review verdict binds to exact requirements revision and source head/tree digest. Any source head change makes verdict and dependent evidence stale. Dirty worktrees require a host-collected tree digest and reproducible snapshot; absent that, results are claims and cannot be host-verified.

Worker outcomes are `ready_for_review`, `blocked`, or `failed`; only the host can record `accepted`, after the current coordinator/acceptor identity, requirements/result/review revisions and existing terminal-transition gate all pass. Every route to terminal task status, including ordinary Tasks tools, must consult a Tasks-owned policy interface supplied at composition. Missing policy for a managed task fails closed. A user override, if available through existing UI authority, is explicit, reasoned and audited; it does not forge a passing review.

Board status names are configurable labels, not state-machine values. Each group stores explicit board status IDs for its approved ready, running, awaiting-review, and accepted mapping; IDs are validated against that board. A category alone is insufficient where a board has multiple active statuses. Internal ledger states remain canonical and independent. A renamed/deleted mapping is surfaced as configuration-needed; it never silently maps an unknown label to accepted/done. `wont_do` is never accepted. Dependency readiness uses task identity and accepted ledger state, not status text.

## 5. Delivery ambiguity and recovery

Dispatch integration is a later phase. The proposed saga uses a stable operation ID and steps `reserved -> session_created -> task_assigned -> prompt_enqueued -> running`. Reconcile a step before retrying it; do not create a second child because an acknowledgement was lost. B5 outbox delivery rules and B7 handoff compensation remain authoritative. Migration 49 itself does not dispatch, create child sessions, or persist the saga operation ID.

If a crash occurs after enqueue/send may have reached the vendor but before a definitive receipt, first reconcile session/turn/queue state. Only after host reconciliation may the host call `MarkAttemptAmbiguous(ctx, attemptID, expectedRevision)` to CAS that selected `prompt_enqueued`/`running` attempt to `interrupted_unknown`; this storage method does not perform liveness checks. It never automatically resends an ambiguous prompt or replays a task with possible side effects. Migration 49 has no retry/release/reassignment API: `current_attempt_id` remains pinned after every attempt outcome. Future retry work must add a host-owned reconciliation path that confirms the prior writer/turn stopped or isolated before releasing/reassigning; do not clear a pointer merely because the attempt is failed or cancelled. Pending permission/question recovery stores metadata only; old requests remain interrupted and unanswerable. App startup never invokes a model by itself.

Progress-only events update the read model and do not wake the coordinator. Later phases may batch actionable events using existing delivery/wakeup paths; event IDs and watermark are acknowledged only after actual prompt inclusion. Pause, open user prompt/queue, pending interaction, locked vault, closed session, or unknown post-restart interaction state blocks auto-wake. Do not implement batching or auto-wake as part of the metadata-only foundation unless explicitly included in that phase's scope.

## 6. Artifacts, budgets, and retention defaults

Migration 49 has no artifact/payload body store and therefore exposes no artifact-write operation. When a later phase adds one, artifacts must be encrypted, immutable by content hash, addressed only by opaque IDs, and readable only after group/workspace/task/attempt scope checks. The approved 200 MB per-group value is a manual ended-group retention threshold, not an artifact quota. Per-artifact, result-summary, brief/checkpoint, and evidence-reference size limits remain proposals from earlier drafts; they are not approved TEAM1 requirements. A future payload phase must define and approve its own bounded limits before implementing writes.

Retention is manual only and applies only to ended groups. Starting configuration is 30 days and 200 MB per group, adjustable by the person. Migration 49 has no payload cleanup or group-delete API. Current group/item/attempt rows are protected by restrictive foreign keys, and attempts remain reachable through the pinned current pointer. Never automatically delete active or referenced records. A future explicit cleanup may leave a tombstone while references remain; purge requires no live references and normal vault deletion semantics. There is no separate workspace artifact quota in this approved contract.

## 7. UI hosting contract

The future Team/Timeline experience is opt-in from the parent task UI and is one group document in Agent Hub, opened with a stable `groupId` param via the existing document helper. Agent Hub's `ModuleManifest.sidebar` remains the only rail; the workbench owns tabs, focus, split, pin, close, and persistence. Do not add a second sidebar, tab strip, group-selection store, or standalone shell. Closing the document does not stop work. Delete/pause/stop actions call host services and respect existing gates. Details and events load by scoped opaque IDs with pagination; deltas carry stable sequence/revision and contain no payload body or transcript. `useModuleVisibility()` gates dialogs; stale actions refresh and do not target a different selection. Existing shell integration rules in `docs/design/module-shell-integration.md` govern implementation. The UI and all later workflow capabilities remain future-phase requirements.

The metadata foundation may ship without Team/Timeline UI. If so, it exposes no new user-facing claim of autonomous team orchestration; existing Agent Hub session tabs and peer controls continue unchanged.
